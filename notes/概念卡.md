## D1｜11/09 概念基础 + 环境验证

- [ ] **LLM**：
  基于 Transformer 解码器、用「预测下一个 token」在大规模语料上自监督预训练，再经指令微调 / RLHF 对齐的模型。输出是概率采样逐 token 生成，知识以参数形式固化在训练截止前的语料里，不查库、不保证事实。
- [ ] **Token**：
  tokenizer（BPE / SentencePiece 等）把文本切成的整数 id，是模型读写的最小单位；一个 token 可能是一个字、半个词、一个标点。中文常见 1 个汉字 ≈ 1–2 个 token，但不同模型差异大，精确值要用官方 tokenizer 实测。输入与输出分别计费，输出通常更贵。
- [ ] **上下文窗口**：
  单次调用能「看见」的 token 总预算：system + 历史消息 + RAG 检索片段 + 用户输入 + 预留给输出的部分，全部共用同一额度；超出报 400 或被滑窗截断，窗口外信息完全不可见。长上下文 ≠ 长期记忆，跨会话记忆靠外部存储 / 摘要 / 检索。
- [ ] **生成式 vs 判别式**：
  教科书定义：生成式建模联合分布 P(X,Y) 或数据分布 P(X)，能产出新样本；判别式建模条件分布 P(Y|X) 或决策边界，只做分类 / 回归（LR、SVM、BERT 分类头）。注意工程口语的「生成式 AI」＝能产出新内容，与教科书定义不完全等同。LLM 是生成式，但加结构化输出就能干判别活。

**面试 20 秒口述版**（一条串起四个概念）：

> LLM 本质是按概率逐 token 续写；token 是它读写的最小单位，system、历史、检索片段和留给输出的空间共享一个上下文窗口预算，所以工程上要精简上下文、用 RAG 挑最相关的片段。它属于生成式模型，但现在分类、判定类任务也常用它加 JSON schema 输出来做，代价是输出不确定，必须做格式校验和兜底。

**高频追问**：① 中文到底几个 token？→ 不背数字，用官方 tokenizer 实测。② 窗口塞满会怎样？→ 报错或丢最早的消息，所以要做历史摘要 / 滑窗。③ 生成式模型凭什么做分类？→ 约束输出到有限标签 + schema 校验；高确定性高并发场景仍用小判别模型更省。

## D2｜11/10 LLM 原理 + Prompt 工程化

**4 个新词**（各 1–2 句自己的话 + 一句「面试怎么说」；别抄名词解释）：

- [ ] **system / user / assistant 角色分工**：`messages` 数组里 system 放长期规则（最前、优先级最高）、user 是本次问题、assistant 是模型之前回过的话；模型本身不记会话，多轮是我把整段历史重新发一遍。面试怎么说：今天 `variant=role` 拒答天气、`none` 却开始教我查天气 App，差别只是一条 system；所以 system 里别塞互相冲突的指令，历史长了要做摘要 / 滑窗。
- [ ] **few-shot**：在 prompt 里放 1–2 组「问 → 答」样例，模型会照着句式和语气输出，属于上下文学习、不改模型权重。面试怎么说：比写十行「请按 XX 格式回答」稳，代价是吃 token；② 组实测把示例段拼进 system 后，输出确实收敛成「不能。根据……」的短句，比无示例时自行展开法条稳定得多。
- [ ] **temperature 与 top_p**：都调采样随机性 —— temperature 把候选概率分布拉平或拉尖，top_p 只从累计概率到 p 的候选里抽；值低更稳、值高更发散。面试怎么说：`deepseek-flash` 思考模式下 temperature 不生效，要先 `reasoning_effort: 'none'` 才测得出差别（今天 0 给短句、0.7 给长句）；补到各 3 次后没有一次逐字相同，**设 0 也不保证复现**，生产靠 schema 校验。另：该模型非思考模式 top_p 恒为 1.0，传值被忽略。
- [ ] **JSON mode**：`response_format: {type:'json_object'}` 让接口只吐合法 JSON，但必须同时在 system / user 里写明「输出 JSON」，否则可能返回空白；它只保证语法合法，不保证字段名符合我的 schema。面试怎么说：今天 `variant=json` 返回纯 JSON、字段正好 `{合规结论, 依据, 风险提示}`，对比 D1 的代码块 + 自创字段 + 免责声明；格式稳定靠「参数 + prompt 指令 + 后端 JSON.parse 校验 / 重试」三层，不能只靠参数。

**今天唯一要能讲清的一句话**（抄写并脱稿复述）：

## D3｜11/11 RAG/Agent 概念 + 聊天 UI 组件化

**两段速记**（用自己的话，别抄名词解释）：

- [ ] **RAG 完整流程**：模型不知道的东西，先替它找出来再交给它，而不是指望它背下来。离线那半段把文档解析、清洗、切成小块（chunk + overlap + 元数据）、算成向量存进库；在线那半段把问题也变成向量去捞最像的几块，可选 rerank 后拼进 prompt（资料 + 指令 + 引用要求），模型照着答并给引用。
  **面试怎么说**：答错了先把召回片段打印出来人工看 —— 里面没有正确答案＝检索的锅，有还答错＝生成 / 拼接的锅，所以评测必须把检索指标和生成指标分开算（D3-Q1 口诀「先分清『没找到』还是『没答好』」）。容易坏的地方依次是：解析坏 / 切错 / embedding 语种不匹配 / 召回不准 / 片段太多撑爆窗口（挂回 D1 的「一份预算」）/ 没引用无法核验；进阶补向量+BM25 混合检索、rerank、元数据过滤做权限。
  **出处**：② 前端人的高光时刻（94 分钟全片已看完）里的 RAG / Prompt 设计 / 前后端 API 集成。
- [ ] **Agent vs RAG**：RAG 治「模型不知道」，Agent 治「模型不能动手」—— 模型提议调工具、代码去执行、结果回灌、它再判断下一步。两者能组合，Agent 可以把 RAG 当成一个工具。
  **面试怎么说**：先问「这活要不要动手」；只查资料回答就 RAG，要操作外部系统才上 Agent（D3-Q2 口诀）。规则固定、可穷举、要求强审计与确定结果的流程，我明确劝客户用工作流 / 规则引擎，别上自主 Agent —— 死循环、工具误用、成本延迟失控、可观测与回放都难做。
  **出处**：② 里「Agent（重点）」那节 + ① 李宏毅 **P18 第 9 讲 AI Agent（11/11 20:41 已看完 ✅）**。两处都讲「模型提议调工具 → 代码执行 → 结果回灌」，今晚 D3-Q2 可以直接拿 P18 当例子。

**今天唯一要能讲清的一句话**（抄写并脱稿复述）：
> RAG 是「先检索到资料，再让模型照着资料答」，治的是知识；Agent 是「模型提议调工具、代码执行、结果回灌」，治的是行动。选型只问一句：这活要不要动手。

**今天动手里值得讲的 3 个点**（组件化，口述版见 `D3_组件化结构设计.md` 第八节）：

- 三层拆分：`useChat.ts` 管状态和 SSE、`Message.vue` 纯展示（props，不 emit）、`App.vue` 只组装。**D1 的 SSE 行缓冲一行没重写**，因为中文跨包不乱码就靠那几行；已用 7 字节小包实测过。
- 自动滚动盯 `messages.at(-1)?.content` 而不是数组长度 —— 流式时条数不变，变的是最后一条的内容；`scrollTop` 还要求容器有固定高度 + `overflow-y:auto`。
- `AbortController` 让用户可以停掉没生成完的流：停止后**保留已出的字**、后台不再烧 token，组件卸载也自动断流。
